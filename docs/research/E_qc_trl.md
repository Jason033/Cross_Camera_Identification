## (a) 框架總覽

### 1. 技術成熟度（TRL）與技術成熟度評估（TRA）
TRL 是 NASA 發展、美國國防部採用的 1–9 級量表，用來描述一項技術從基本原理到實戰運用的成熟程度。TRA 則是依此量表由獨立人員對「關鍵技術元件」逐項評級的正式作業。美國國防部 2023 年 6 月版 TRA 指引與 GAO-20-48G 都是公開的權威參考。GAO 指引的重點之一是：評級必須有證據支持，而且系統整體等級取決於最弱的關鍵元件。
- 來源：DoD TRA Guide（2023）https://www.cto.mil/wp-content/uploads/2023/07/TRA-Guide-Jun2023.pdf [推論：確認網址與標題存在，未開啟]
- 來源：GAO-20-48G https://www.gao.gov/products/GAO-20-48G [推論]
- 來源：NASA TRL 定義 https://www.nasa.gov/wp-content/uploads/2017/12/458490main_trl_definitions.pdf [推論]

### 2. 製造成熟度（MRL）
MRL 是美國國防部的 1–10 級量表，評估技術能否被穩定、可負擔地製造。研究階段的專案通常只需知道它的存在，在 TRL 5–6 以後才會成為主要議題。美國國防部另有 MRL Deskbook，這次只找到第三方介紹與 DTIC 文件的標題。
- 來源：https://acqnotes.com/acqnote/tasks/manufacturing-readiness-level [推論]
- 來源：https://apps.dtic.mil/sti/tr/pdf/ADA510027.pdf [推論]

### 3. 整合成熟度（IRL）與系統成熟度（SRL）
IRL 衡量元件之間介面與整合到什麼程度；SRL 由 Sauser 等人提出，把各元件 TRL 與元件間 IRL 合併成系統層級指標。對「跨攝影機」專案，各攝影機、偵測、追蹤、重識別（Re-ID）模組之間的資料介面，正是 IRL 的概念對應處。
- 來源：Sauser 簡報 https://ndia.dtic.mil/wp-content/uploads/2006/systems/Thursday/sauser.pdf [推論]
- 來源：NPS 報告 https://www.dair.nps.edu/bitstream/123456789/106/1/NPS-AM-08-060.pdf [推論]

### 4. 機器學習技術成熟度（MLTRL）
Lavin 等人 2022 年發表於 Nature Communications，是目前最完整、可直接用於 AI 專案的公開框架，共 0–9 級（比傳統 TRL 多一個 Level 0）。核心特色是每一級都有明確的審查關卡、必備成果，並使用「TRL Card」文件記錄各級證據。細節見第 (c) 節。
- 來源：https://pmc.ncbi.nlm.nih.gov/articles/PMC9585100 [證實]
- 預印本：https://arxiv.org/pdf/2101.03989 [推論]

### 5. NASA 軟體 TRL 與系統工程流程
NASA 的 NPR 7123.1 附錄將 TRL 定義延伸到軟體與系統工程流程，並含有審查節點。可用來補充「軟體在 TRL 各級要做什麼」。
- 來源：https://explorers.larc.nasa.gov/HPSMEX/SMEX/pdf_files/N_PR_7123_001B__Change_3.pdf [推論]

### 6. 美國國防部負責任 AI 工具包與 AI 測評框架
CDAO 於 2023 年底發布 Responsible AI Toolkit，用於把 AI 倫理原則落實到專案生命週期各階段的檢查項目；2024 年 4 月另發布 T&E 框架文件（模型、系統整合、人機整合、作戰測評等）。這兩者不是成熟度量表，而是 AI 專案「該檢查什麼」的清單，適合作為月報中「風險與品質」章節的參照。
- 來源：https://www.ai.mil/Latest/Blog/Article-Display/Article/3940314/responsible-ai-toolkit/ [推論]
- 來源：https://www.ai.mil/Latest/Blog/Article-Display/Article/3940283/cdao-test-and-evaluation-strategy-frameworks/ [推論]

### 7. 品質管理系統：ISO 9001 / AS9100
AS9100 是航太、航空與國防組織的品質管理要求，建立在 ISO 9001 之上。**我沒有找到中科院本身取得這些驗證的公開文件**（見第 (f) 節）。對你的專案而言，ISO 9001 的實用部分是「設計與開發管制」的概念：規劃、輸入、管制、輸出、審查、驗證、確認、變更管制。這些可轉成月報的固定項目。
- 來源：DNV AS9100 介紹 https://www.dnv.com/tw/services/as-9100-aerospace-quality-management-3279/ [推論]

## (b) TRL 1–9 中文對照與 AI／軟體證據

### 關於中文用詞的重要說明
我只實際取得一份中文 TRL 定義：農委會農業試驗所人員 2018 年的文章（https://www.moa.gov.tw/ws.php?id=2508834 ）[證實]。它用的詞是「技術準備度」，而且是農業專用的改寫版（例如 TRL4 寫「現場試驗」），與國防或國科會用語不同。**我沒有找到國科會或經濟部技術處的官方 TRL1–9 中文逐級定義。** 下表的中文為依 NASA／DoD 英文定義的意譯 [推論]，正式報告請用貴單位指定用語。

| TRL | 中文意譯（推論） | AI／軟體可作為證據的成果 |
|---|---|---|
| 1 | 觀察到基本原理 | 文獻回顧、問題定義、使用情境與營區需求描述、既有方法比較 |
| 2 | 形成技術概念與應用構想 | 方法設計文件、初步系統架構、假設與成功指標、資料需求清單、公開資料集上的初步實驗 |
| 3 | 關鍵功能的分析與實驗性概念驗證 | 在公開基準（如 Market-1501 等）或模擬資料上可重現的實驗；程式碼版本管理；對比基線的結果；失敗案例分析 |
| 4 | 在實驗室環境驗證元件或原型 | 以接近營區的代表性資料（取得授權後）驗證；端到端管線原型；明確的評估指標（如 Rank-1、mAP、跨鏡頭 ID 切換率）；限制說明 |
| 5 | 在相關環境驗證元件或系統 | 在模擬或試驗性的營區攝影機網路上驗證；整合測試；效能（延遲、吞吐量）報告；資料治理與資安審查 |
| 6 | 在相關環境展示系統原型 | 完整原型於試驗營區運行；穩健性測試（光線、天氣、遮蔽）；使用者回饋 |
| 7 | 在實際作業環境展示原型 | 在實際營區實地運行；實際作業資料的長時間表現；維運文件 |
| 8 | 系統完成並通過驗證 | 完整測試與鑑定報告；操作手冊；訓練教材；安全與合規核定 |
| 9 | 系統在實際任務中證明可行 | 長期運行監控；資料漂移監測；維護紀錄 |

**實務提醒（推論）**：對 AI 專案而言，TRL3 與 TRL4 的分界通常取決於「資料是否具代表性」，而不是模型是否更準。若只用公開資料集，通常不宜自評超過 TRL3。MLTRL 在 Level 4 明確要求使用真實代表性資料與使用者相關指標，這一點可作為依據（見下節）。

## (c) MLTRL 摘要與對應 TRL

以下內容 [證實] 取自論文全文（https://pmc.ncbi.nlm.nih.gov/articles/PMC9585100 ）。論文並未提供 MLTRL 與傳統 TRL 的逐級對照表，右欄的「對應傳統 TRL」是我的推論。

| MLTRL | 名稱 | 主要要求與證據 | 審查重點 | 對應傳統 TRL（推論） |
|---|---|---|---|---|
| 0 | 第一原理 | 文獻、數學基礎、初步構想，並考慮資料可得性；開始建立 TRL Card | 實驗室主管檢查數學有效性與新穎性 | 約 TRL1 |
| 1 | 目標導向研究 | 在樣本（可為合成）資料上做低層實驗；研究級程式碼；程式、模型、資料皆做版本管理 | 研究團隊同儕審查 | 約 TRL1–2 |
| 2 | 原理驗證 | 測試平台或模擬資料；正式研究需求與驗證確認步驟 | 研究主張可重現，決定進入原型或繼續研究 | 約 TRL2–3 |
| 3 | 系統開發 | 原型級程式碼附測試與文件；專用測試資料子集 | 檢查軟體實務、介面、版本管理 | 約 TRL3 |
| 4 | 概念驗證 | 真實代表性資料；貼近使用者的指標；資料管線概念驗證；倫理考量 | 展示效用、說明限制、檢查資料品質、安全與隱私；決定繼續或暫停 | 約 TRL4 |
| 5 | ML 能力 | 跨領域工作小組；以展示或 API 分享技術；起草產品需求與驗證確認；資料治理 | Level 2 的驗證確認須完成；需求對齊利害關係人 | 約 TRL4–5 |
| 6 | 應用開發 | 產品級程式碼、完整測試與 API；穩健性檢查；定義部署情境；合規 | 程式品質、需求、服務水準、資料管線規格、倫理再檢視、法規遵循 | 約 TRL5–6 |
| 7 | 整合 | 關鍵情境測試；黃金資料集；變形測試與資料干預測試 | 審查資料管線與測試套件 | 約 TRL6–7 |
| 8 | 任務就緒 | 最終形態測試；影子、金絲雀等線上測試；自動記錄資料分佈 | 逐項需求走查，全體利害關係人會審；決定走或不走 | 約 TRL7–8 |
| 9 | 部署 | 監控資料與概念漂移；維護工程；變更退回 Level 7 或更早 | 定期由擁有者審查 | TRL9 |

論文另指出，系統的 TRL 等於其最低元件的 TRL。這對多模組的跨鏡頭辨識系統特別重要：偵測、追蹤、特徵萃取、跨鏡頭關聯，各自等級可能不同，月報宜分模組列示。

**對你專案的建議**：目前若為 TRL1–3，月報可直接採用 MLTRL 的 Level 0–3 作為內部檢查表（版本管理、可重現實驗、測試資料切分、同儕審查），再對外以傳統 TRL 表達。

## (d) 系統工程審查關卡

審查關卡名稱與用途源自 MIL-STD-1521B（技術審查與稽核），並與 ISO/IEC/IEEE 15288、24748-2 的技術審查概念相近。下表中文名稱為常見譯法 [推論]，國軍內部實際用語請以貴單位文件為準。我找到 MIL-STD-1521B 的標題與 DTIC 副本（https://apps.dtic.mil/sti/pdfs/ADA633324.pdf ）及 DoD 15288 指引（https://ac.cto.mil/wp-content/uploads/2019/06/15288-Guide-2017.pdf ），但未開啟。

| 縮寫 | 英文 | 常見中文名稱 | 目的 | 對 TRL1–3 AI 專案的適用度 |
|---|---|---|---|---|
| SRR | System Requirements Review | 系統需求審查 | 確認需求已被理解且可行 | 高：可用作專案啟動審查 |
| SFR | System Functional Review | 系統功能審查 | 確認功能配置與需求一致 | 中 |
| PDR | Preliminary Design Review | 初步設計審查 | 確認初步設計能滿足需求，風險可控 | 中：TRL3 末可做簡化版 |
| CDR | Critical Design Review | 重要（關鍵）設計審查 | 確認詳細設計可進入製作 | 低：TRL5 以後 |
| TRR | Test Readiness Review | 測試整備審查 | 確認測試前人員、環境、程序就緒 | 中：進行實地測試前使用 |
| PRR | Production Readiness Review | 生產整備審查 | 確認可量產 | 不適用 |
| FCA | Functional Configuration Audit | 功能構型稽核 | 確認成品功能達到需求 | 不適用 |
| PCA | Physical Configuration Audit | 實體構型稽核 | 確認成品與設計文件一致 | 不適用 |

[推論] 研究階段專案不需要全套審查；建議只採用 SRR（需求）與簡化版 PDR（概念設計）兩個節點，其餘留到專案轉入工程發展階段。

## (e) 月報骨架（適用 TRL1–3 的 AI 研究專案）

此骨架結合經濟部查核點做法 [證實] 與一般政府計畫月報慣例 [推論]。國科會期中報告格式我只找到各大學轉載的公告標題（例如 https://ord.nccu.edu.tw/files/rd_research/542_5abfe218.pdf ），未開啟，所以未直接引用其欄位。

**月報 一頁摘要**
1. **本月一句話結論**：目前自評 TRL（分模組）、較上月是否變動、變動的證據。
2. **工作項目與進度表**：工作項目、預定累計進度、實際累計進度、差異原因。（經濟部 75% 門檻是參考，可作為內部紅黃綠燈標準）
3. **查核點狀態**：查核點編號、內容（具體、可驗證、可量化）、預定日期、狀態、佐證檔案。每季至少一個。
4. **本月成果**
   - 實驗結果表（資料集版本、模型版本、指標、與基線差異）。
   - 可重現證明（程式碼雜湊值、隨機種子、環境說明）。
   - 失敗與負面結果同樣列示。
5. **成熟度自評（固定格式）**
   | 模組 | 目前 TRL | 下一級進入條件 | 缺口 | 預計達成月份 |
   |---|---|---|---|---|
   | 偵測 | | | | |
   | 單鏡頭追蹤 | | | | |
   | 特徵萃取／Re-ID | | | | |
   | 跨鏡頭關聯 | | | | |
6. **資料管理**：資料來源、授權、機敏性分級、去識別化、儲存位置。（營區人員影像涉及個資與機敏，這一項應固定列出）
7. **問題與對策**：問題、影響、對策、負責人、期限。
8. **風險登錄**：技術風險（如跨鏡頭外觀變化）、資料風險、資安風險、進度風險。
9. **下月計畫與資源需求**。
10. **決策請求**：需要主管決定的事項（例如是否進入 TRL4 所需的真實資料蒐集）。

**維持專案不失焦的作法（推論）**：
- 每季只設一個主要研究問題，月報其他項目服務於它。
- 每個新增工作都要回答「推進哪一個模組的哪一級 TRL」，答不出來就列為待辦。
- 保留固定的「不做的事」清單。
